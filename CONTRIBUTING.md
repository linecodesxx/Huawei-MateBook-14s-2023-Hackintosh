# Как обновлять проект

## Один эксперимент — один понятный результат

Используйте [шаблон](experiments/TEMPLATE.md). Записывайте фактически загруженную конфигурацию, изменение, ожидаемый признак, наблюдение и вывод.

- Собрано — файлы созданы.
- Проверено статически — валидатор/проверка зависимостей прошли.
- Проверено загрузкой — есть результат конкретного запуска на этом ноутбуке.
- Стабильно — подтверждено повторениями и нагрузкой, а не одним успешным стартом.

Не отмечайте checkbox только потому, что создан файл или применился патч. Если эксперимент не проводился, пишите «не проводился».

## Работа с Codex

Сначала прочитать текущий статус и журнал локальных изменений. Более свежие локальные результаты не откатывать под старую документацию.

Агент готовит отдельную сборку, фиксирует зависимости и предлагает один следующий тест. Физическую загрузку и наблюдение выполняет владелец ноутбука. Агент не должен придумывать результат.

После подтверждённого результата обновить docs/STATUS.md и ROADMAP.md; для существенного этапа добавить devlog.

## Проверка перед публикацией

```sh
git diff --cached
python3 scripts/check_publication.py
python3 -m unittest discover -s tests -v
```

Установить локальную проверку:

```sh
git config core.hooksPath .githooks
```

GitHub web editor и изменения через API обходят локальный hook. Их содержимое нужно проверять отдельно. Не прикладывать исходные EFI/дампы в Issues: используйте очищенные минимальные фрагменты.

У сторонних патчей указывать источник, commit и лицензию.
