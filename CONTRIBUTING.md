# Как обновлять проект

**Русский** | [English](CONTRIBUTING.en.md)

## Один эксперимент — один понятный результат

Используйте [шаблон](experiments/TEMPLATE.md). Записывайте фактически загруженную конфигурацию, изменение, ожидаемый признак, наблюдение и вывод.

- Собрано — файлы созданы.
- Проверено статически — валидатор/проверка зависимостей прошли.
- Проверено загрузкой — есть результат конкретного запуска на этом ноутбуке.
- Стабильно — подтверждено повторениями и нагрузкой, а не одним успешным стартом.

Не отмечайте checkbox только потому, что создан файл или применился патч. Если эксперимент не проводился, пишите «не проводился».

## Работа с Codex

Сначала прочитать текущий статус и журнал локальных изменений. Более свежие локальные результаты не откатывать под старую документацию.

Агент готовит отдельную сборку, фиксирует зависимости и предлагает один следующий тест. Физическую загрузку и наблюдение выполняет владелец ноутбука. Агент не должен придумывать результат.

После подтверждённого результата обновить docs/STATUS.md и ROADMAP.md; для существенного этапа добавить devlog.

## Языки документации

Русский — основной язык: README.md и файлы без языкового суффикса содержат исходные версии. Английские переводы имеют суффикс .en.md. README.ru.md сохраняет старую ссылку и направляет к главному русскому README.

Наблюдения, статусы, checkbox, версии, хеши и ссылки должны совпадать в обоих языках. При изменении документа или добавлении devlog обновляйте перевод и обе страницы навигации в том же изменении. Если перевод ещё не обновлён, явно укажите это.

В выборе шаблонов Issues русские варианты идут первыми; язык указан в названии. Переводите вопросы и правила приватности, сохраняя технические идентификаторы.

## Проверка перед публикацией

```sh
git diff --cached
python3 scripts/check_publication.py
python3 -m unittest discover -s tests -v
```

Установить локальную проверку:

```sh
git config core.hooksPath .githooks
```

GitHub web editor и изменения через API обходят локальный hook. Их содержимое нужно проверять отдельно. Не прикладывать исходные EFI/дампы в Issues: используйте очищенные минимальные фрагменты.

Поддерживайте краткую [выжимку результатов](devlog/2026-11-05-recovery-and-input.md) и [основные настройки JSON](docs/recovery-settings.json), проверяя их вручную по [правилам приватности](PRIVACY.md). Публикуйте только существенные наблюдения и собственные ACPI-патчи; полный архив экспериментов и исторические конфигурации храните локально. Указывайте источник и преобразование, оставляйте идентификаторы пустыми. Не переносите рабочие plist, бинарные сборки, родные DSDT, полные EFI или фотографии. Разрешённые общие GUID перечислены в правилах; для остальных UUID исключения не делать. Прохождение проверки публикации не означает проверку загрузки.

У сторонних патчей указывать источник, commit и лицензию.
